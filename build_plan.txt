1. What we are building
A volunteer accepts a task on OpinionPadi, is sent to Voxelion through a secure signed link, gives consent, fills in an intake form, uploads a face photo, and completes a live video challenge. On success they get a unique completion code, which they take back to OpinionPadi as proof. A reviewer approves or rejects the reward — backed by a server-side code check, not just the screenshot. Key principles:
Consent is recorded before any photo is collected. Withdrawal is possible at every step and triggers stop-processing + deletion. The completion code is validated against the backend record; the screenshot is supporting evidence only.

WHY LARAVEL + INERTIA + REACT
One codebase, one deploy. The verification journey is linear and server-driven — Inertia gives React interactivity while Laravel middleware enforces the step order server-side (a volunteer cannot reach /photo before consent is recorded — the route simply won't render). React handles the interactive parts: checkbox gating, getUserMedia camera capture, upload previews. OpinionPadi only talks to the /api/v1/ endpoints — it never sees the frontend. Reviewer screens can be Inertia pages too, or live in the existing Laravel admin app.

State machine enforced server-side: CREATED → CONSENTED → INTAKE_DONE → PHOTO_OK → LIVE_CHECK → VERIFIED / FAILED / MANUAL_REVIEW (+ WITHDRAWN / DECLINED terminal states). The EnforceSessionState middleware sits on every journey route and redirects/rejects out-of-order access — e.g. no /photo render before CONSENTED . Session state lives server-side, so a network drop resumes from verification_sessions.state on next page load.

4.4 COMPLETION CODE RULES (PROPOSED)
Format: VX-XXXX-XXXX-XXXX (Crockford base32, no ambiguous chars), stored hashed. Bound to one participant_id + task_id + session_id . Single-use for reward approval; expires after TBD (suggest 72 h). Validation checks: exists, not expired, not already consumed, session status = VERIFIED.

7. Phased plan
Two parallel tracks — backend and frontend — running through seven phases. No fixed timeline is attached; each phase lists its deliverables and its exit criteria (what must be true before moving on), so progress is measured by completion, not dates.
PHASE 0 — DISCOVERY & DECISIONS Purpose: close every open decision before code is written. This phase is a hard blocker — later phases inherit its outputs. Backend / platform:
Confirm whether Voxelion exposes a face-verification API or SDK. If yes: document endpoints, auth, response format, limits. If no: shortlist providers — NIST FRTE West-Africa results required (see FACE_MATCHING_RESEARCH.md )
Decide inter-platform auth: token format, signing keys (RS256), key rotation, token TTL Decide session rules: expiry, duplicate-session handling, resume behaviour Agree retry limits for photo upload and liveness failures
